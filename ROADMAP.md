#### Фаза 1 — Данные и окружение (3–4 дня)

✅**1.1 Синтетическая SQL-база**
Генерируешь через LLM реалистичную SQLite-базу с 3–4 таблицами:

```
objects       — строительные объекты (id, name, city, budget)
works         — виды работ (id, object_id, work_type, unit)
progress      — прогресс (id, work_id, plan_vol, fact_vol, date)
contractors   — подрядчики (id, name, work_id)
```

Заполняешь ~500–1000 строк синтетическими данными. Это позволит демонстрировать сложные JOIN-запросы.

**1.2 Синтетическая документация для RAG**
Берёшь 5–10 открытых PDF-файлов: СНиП, ГОСТ, образцовые регламенты (есть в открытом доступе). Это реальные документы — огромный плюс на собеседовании.

#### Фаза 2 — SQL-слой (4–5 дней)
Это самая «продаваемая» часть — Text-to-SQL с валидацией.

**2.1 Схема в промпте**
Генерируешь текстовое описание схемы БД + уникальные значения ключевых колонок — кладёшь в системный промпт LLM.

**2.2 Пайплайн**
```
Вопрос → [LLM + схема] → SQL → sqlglot (валидация) → БД → Результат → [LLM] → Ответ
```

**2.3 Retry-механизм**
При `ParseError` от sqlglot — возвращаешь текст ошибки в LLM, до 3 попыток. Точно как в проде.

**2.4 Golden Dataset**
Составляешь 30–50 пар «вопрос → эталонный SQL» — используешь для Few-shot примеров в промпте и для замера `Execution Accuracy`.

---
#### Фаза 3 — RAG-слой (5–6 дней)

**3.1 Парсинг документов**
```python
# Docling — тот же инструмент что в проде
from docling.document_converter import DocumentConverter
```

Чанкинг: размер **480 токенов** (под seq_len эмбеддера 512), с перекрытием 50 токенов.

**3.2 Индексация в Qdrant**
Hybrid Search = Dense (multilingual-e5-large) + BM25 (через `qdrant-client` sparse vectors). Именно эта комбинация — из твоего проекта.

**3.3 Retrieval-пайплайн**
```
Вопрос → Hybrid Search → Top-10 → [Reranker] → Top-3 → LLM → Ответ
```

Reranker: `BAAI/bge-reranker-v2-m3` — тот же что в Проекте 5, можно вынести как общий компонент.

**3.4 Оценка через RAGAS**
```python
# В ноутбуке
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision
```

Синтетический **"golden"** датасет из 20–30 пар «вопрос — эталонный контекст — ответ».

---
#### Фаза 4 — Planner Agent (4–5 дней)
Это ключевой элемент архитектуры — агент, который решает, какой слой вызывать.

**4.1 Логика планировщика**
```python
# Простой router через LLM или правила:
# "сколько объектов сдано?" → SQL-слой
# "что говорит СНиП про фундамент?" → RAG-слой  
# "сколько отклонение от норматива?" → оба слоя
```

**4.2 Инструменты агента (Tools)**
```python
tools = [
    sql_query_tool,      # Text-to-SQL
    rag_search_tool,     # Hybrid Search + Generate
]
```

Реализуешь через LangGraph (стейт-машина) или через нативный tool_use API (Claude/OpenAI). LangGraph предпочтительнее — он у тебя в навыках.

**4.3 Граф агента**
```
START → Planner → [SQL Tool | RAG Tool | Both] → Synthesizer → END
```

### 💡 Что делает этот pet-проект сильным на собесе

1. **Реальная архитектура** — полное соответствие тому, что уже в проде
2. **Измеримые метрики** — Execution Accuracy, Faithfulness через RAGAS
3. **Retry-логика** — не просто "вызвал LLM", а обработка ошибок
4. **Hybrid Search** — не просто векторный поиск, а Dense + BM25 + Reranker
5. **Видимый reasoning** — в UI видно, какой инструмент агент выбрал и почему
6. **Один `docker-compose up`** — можно запустить прямо на собесе
